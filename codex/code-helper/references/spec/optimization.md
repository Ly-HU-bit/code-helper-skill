#这是一份关于code算法优化的要求

#要求
Quick 模式只处理明显且高置信度的复杂度缺陷，不逐方法生成复杂度表。
Standard 模式分析非简单方法并落实有意义的实现级优化。
Deep 模式才执行下方完整检查清单和逐方法复杂度审计。

不要擅自更改用户代码架构，可以更改某些函数的实现方式（如果必要），但如果提升作用巨大，在output.doc文件中向用户说明；
如果用户当前函数实现的时间、空间复杂度均可优化，直接修改，并在doc文件中说明
在内存空间充足的情况下，优先优化时间复杂度
如果有代码或最优解可以通过import解决，在doc文件中说明；

#执行检查清单
进行优化分析时，逐项检查以下内容：

##复杂度分析（每个方法）
- [ ] 标注了当前时间复杂度和空间复杂度（大O表示法）
- [ ] 标记了哪些方法可以优化复杂度
- [ ] 优化后重新标注了复杂度

##优化优先级
- [ ] 优先优化时间复杂度（在内存充足的前提下）
- [ ] 当时间和空间都可优化时，直接修改代码
- [ ] 以下情况仅在doc中说明，不修改代码：
  - 优化需要改变程序架构（需用户许可）
  - 优化提升极小（如常数级改进）
  - import即可解决（如使用标准库替代手写算法）

##常见优化模式
- [ ] 嵌套循环 → 单遍扫描（O(n²)→O(n)）
- [ ] 重复计算 → 缓存/记忆化（memoization）
- [ ] 线性搜索 → 哈希表查找（O(n)→O(1)）
- [ ] 冒泡/插入排序 → 快速/归并排序（O(n²)→O(n log n)）
- [ ] 递归无记忆 → 动态规划
- [ ] String拼接 → StringBuilder/StringBuffer（Java）
- [ ] 逐元素操作 → 向量化/流式操作

##边界判断
- [ ] 对于n≤100的小规模输入：不强制优化O(n²)算法
- [ ] 对于n≥10⁴的输入：O(n²)必须优化
- [ ] 内存消耗在典型JVM/Python进程限制内不做空间优化

##文档要求
- [ ] doc中按方法列出了复杂度分析
- [ ] 有实际修改的方法说明了优化前后的差异
- [ ] 仅建议未修改的优化标注了原因
